# Devlog: Completing the MVP — Phases 3 through 9

Updated: 2026-07-24 16:00  
Author: Lichen Zhu  
Baseline commit: `c5f91ef Add report command: interactive single-file HTML attention dashboard`

## Summary

The remaining MVP phases are implemented: the workday model, browser context,
activity classification, deliverables and tasks, distraction alerts, the daily
review backed by a local LLM, and login autostart. The web console was extended
to surface all of it.

The project still has zero third-party Python dependencies.

## The line that shaped every decision

Phases 0-2 established one rule: **raw samples are the only long-lived fact,
everything explanatory is derived at query time.** Extending that rule to the
new phases decided most of the design:

| Stored (a fact, or something the user said) | Derived at query time |
| --- | --- |
| raw samples, workday sessions, pauses | activity + attention segments |
| deliverables, tasks, the daily note | activity category |
| manual classification corrections | missing-data intervals |
| distraction events and their reasons | deliverable time attribution |
| the generated review markdown | category and per-deliverable totals |

The payoff is concrete: `classify correct process "obsidian" productive_core`
re-labels *every past day*, not just future ones, because no day ever stored a
category. Same for changing an attention threshold or a deliverable's keywords.

## Phase 3 — workday

A workday is not a calendar day. `workday_key_for` assigns anything before the
configured start time (capped at 05:00) to the previous day, so a session that
ends at 02:30 still lands on the review for the day it began.

`describe()` derives elapsed / paused / worked, and clamps to
`max_workday_hours` — a session left open for 30 hours is a data bug, not a
shift, and should not silently become a headline number.

**Missing data** is derived from gaps in the heartbeat table rather than
recorded by a watchdog. A gap counts once it exceeds three poll intervals. This
matters for honesty: the review prints how long the agent was not running, so
the user is never shown statistics that quietly omit an hour.

## Phase 4 — browser context (title parsing route)

No extension, so the only signal is the window title. `browser.py` strips the
browser suffix and recovers a site, either from a page-title fingerprint
("… - Stack Overflow") or from a domain written into the title.

The domain matcher needed a real fix during testing: the first version required
three labels, so `docs.rs` was missed; relaxing it to two labels then matched
`main.py` and `report.rs` as websites. Resolved with a file-extension deny list
plus a TLD list, and a trailing-slash escape hatch so `docs.rs/tokio` is a site
while `main.rs` is a filename.

Redacted titles are never mined — `[private browsing]` yields no site.

## Phase 5 — classification

Eleven categories, resolved most-specific-first exactly as the spec's priority
list: manual correction → deliverable link → site → process → title keyword →
unknown.

Two details worth keeping:

* A browser process alone never decides a category. Chrome is not a category;
  what is *in* Chrome is.
* Video and search sites are split by page title, so a lecture on YouTube is
  `learning_general` while a gameplay video is `entertainment` — the exact
  example the spec called for.

`classify unknown` ranks unlabelled time by duration so the user fixes the
biggest gap first, and prints the exact command to fix it.

## Phase 6 — deliverables

Time is attributed to a deliverable by keyword match against process name and
window title. Segments matching nothing are simply not attributed — inventing a
link would make the progress figures lie.

A bug caught while driving the CLI: `deliverable list` showed *effective* time
equal to raw time, because attention weighting only happened on the review path.
The weighting helper moved into `classify.attach_attention_weight` and both
paths now use it. Without it, a window left open while the user is away counts
the same as a window being worked in.

`stalled_deliverables` reports active deliverables that got no time — the thing
a review actually needs to say out loud.

## Phase 7 — distraction alerts

`DistractionTracker` keeps a category streak in memory inside the agent loop
and fires when a threshold is crossed, subject to a cooldown. The check is
wrapped so it can never take down a sample: classification is pure, and any
failure is logged and dropped.

Alerts are *recorded*, not just shown. The CLI then asks why, from the spec's
reason list. A distraction count with no reason is a number that shames the
user instead of informing them; the labelled reason is what reaches the review.

## Phase 8 — local LLM review

The user asked for a small local model rather than a cloud API, which fits the
project better than the original plan did: the day's data never leaves the
machine and nothing costs money.

`llm.py` talks to an Ollama-compatible endpoint over the loopback interface
using only `urllib` — no dependency added. `probe()` distinguishes "server not
running" from "model not pulled" and the CLI prints the exact fix.

**The division of labour is the whole design.** Python computes every figure and
writes every factual section. The model receives a short briefing of finished
numbers and writes exactly two prose sections. It is never asked to add up
seconds, read a timeline, or recall a fact. That is what makes a 1.5B model
useful here: a weak model produces weaker wording, never wrong numbers. A test
asserts the briefing contains no raw rows.

Degradation is complete, not partial: with no model reachable the review is
generated deterministically, saved, and marked `llm_status = failed` with the
reason. Small models also drift off the requested format, so missing headings
are repaired rather than trusted.

## Phase 9 — autostart

launchd on macOS, Task Scheduler on Windows, `systemd --user` on Linux. No
resident supervisor, no dependency, and uninstall leaves nothing behind.
`status()` never raises on any platform, because a silent failure here is only
discovered days later when a day comes back empty.

## Web console

The API grew `workday`, `categories`, `deliverables`, `distractions` and
`review` blocks; the React app grew a category band aligned to the existing
rows, hatched missing-data regions, workday start/end markers, distraction
pins, and three panels (categories scoped to the visible range, deliverable
progress, the rendered review).

## CLI structure

Nine new command groups would have pushed `cli.py` past 1400 lines. Shared
helpers moved to `cli_support.py` and the new groups live in
`focusledger/commands/*`, registered through one list. Existing commands were
left alone, so the refactor carried no risk to working code.

## Open edges

- Deep-work thresholds (25 min / 5 min slack) are still frontend constants and
  belong in `AppConfig` beside the attention thresholds.
- Distraction detection recomputes `load_rule_context` every sample. Fine at a
  5 s poll; worth caching if the poll rate drops.
- The offwork prompt is a CLI flow (`workday offwork` → `review write`), not the
  interactive terminal menu the spec sketches. The menu needs a resident
  foreground process, which conflicts with the background agent model.
- Review prose quality with a 0.5-1.5B model is untested here — no model is
  installed in this environment. The deterministic path is fully exercised.
